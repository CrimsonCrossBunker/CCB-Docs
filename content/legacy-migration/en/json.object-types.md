## CCB JSON object-type registry

Native `DynamicDataLoader::add(type, handler)` calls define recognized object types.
`data/reference/json/ccb_json_object_types.json` is a checked inventory generated by
`tools/json_api/generate_contracts.py`. It currently covers 191 registration calls and 190 unique
types. That proves discovery and indexing, not a complete field Schema for every handler.

### Using the inventory

Each entry records type, handler, source symbol and line, provable mandatory or optional fields,
first-party examples, and documentation status. Interpret `schema_status` and
`documentation_status` literally. `unclassified` or lexical-only evidence cannot be promoted into
requiredness, defaults, or complete support.

Never hand-edit generated inventories. After registration, handler, or example changes, run the
generator, repository JSON formatter, `--check`, and `tools/json_api` unit tests. If a complex reader
cannot be proven, extend auditable extraction or add non-behavioral registration metadata rather
than guessing.

### From type to authoritative contract

1. Find the handler and source in the inventory.
2. Read its `mandatory`, `optional`, custom readers, finalization, and checks.
3. Find a nearby first-party JSON example and focused test.
4. Inspect IDs, copy-from, deferred loading, units, translation, migration, and Mod boundaries.
5. Validate the real combination with formatting, `make -j2 json-check`, and `--check-mods`.

An editor Schema can assist completion, but loaders and tests win. Occurrence counts show sample
frequency, not requiredness. Successful parsing does not prove cross-ID finalization, balance, or
save compatibility.
